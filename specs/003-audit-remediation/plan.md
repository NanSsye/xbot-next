# 技术方案：复核并修复 Hermes 升级后告警

## 关键假设
- **CRITICAL**：只修改本地新版，使用公开发行记录、合成测试数据，不接触线上容器和凭据。
- **CRITICAL**：依赖保持现有来源；Hermes 的实际版本仍由发行清单和校验和决定，扫描器占位版本不作为定案证据。
- 复用 `uv`、npm、PDF 提取器、MCP SDK 和 `pg`；不新增服务或业务依赖。

## 实施与风险
- 后端定向升级现有 Python 包；解除项目的 `pypdf<6` 限制，兼容性靠附件回归验证；MCP 采用 Hermes 上游同版本约束，核对两个传输客户端及插件入口。
- HTTP MCP 改用 SDK v2 的传输入口；复用已锁定的 httpx2 来传递配置的请求头和超时。每条连接由同一个后台任务打开和关闭 SDK 上下文，支持跨任务重载。用实际 SDK 验证调用、重载和退出。
- 前端使用 npm 兼容范围修复保留原构建和应用入口。继续用锁文件构建生产静态文件。
- 目录表保留本项目文件，旧 Hermes 快照按目录整体登记；记录审计前后数量和未修复项。无 API、数据模型或迁移变更。
- 同步 Python 和前端依赖配置节点及目录说明；如功能回退，仅还原本任务的依赖清单和对应锁文件，不回滚已有改动，已知风险需重新评估后再发布。
