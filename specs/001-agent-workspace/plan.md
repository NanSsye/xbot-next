# 实施方案

## 服务器基线迁移

CRITICAL：以 `server-ui.sha256` 固定已部署前端基线。只在独立的 `xbot-next-server-baseline` 目录工作，不改服务器、旧工作树或第三方依赖。先检查线上 API、仓储、Agent 适配层的差异，再复用旧原型里的工作台和测试；共享 UI 主题使用服务器现有令牌及 Markdown 组件。真实模型钥匙、通道和数据库不用来验收本地预览。以下初版步骤按新基线重新验收。

## 独立部署

从当前 SQLAlchemy 元数据生成冻结的初始迁移，验证空 SQLite 升级、降级和再升级，并检查 PostgreSQL 离线 DDL；历史升级链不进入新部署。保留 PostgreSQL、Redis 和原服务入口。用独立 Compose 项目，默认只监听回环地址，强制 API Token。回退是继续使用旧实例，不能把两个实例指向同一个数据库。旧静态媒体访问规则在对其他网段开放前还需单独审查。

## 原型实施记录

1. 移除社区专属前端、后端、插件和模型注册，确保 API 不再暴露、Agent 不再加载社区工具。
2. 参考 SYNDEX 的 `ChatTitleBar`、`WelcomeScreen` 与 `ChatInput`，在 Xbot 独立工作台复用现有消息渲染与任务持久层。每个新对话用独立来源键；旧 `terminal:control-ui` 仍可回看。用任务 ID 建立流事件与消息的对应，发送前同步上锁，切换会话不混淆草稿与回复。
3. 现有任务 API 保持兼容，新增专用网页会话流及历史过滤；验证中文 IME、相同消息、错误、任务事件、旧会话与回看。不把客户端断开误报成已终止模型后台执行。
   按用户截图移除仅 Agent 对话页渲染的横幅及其统计请求，不影响其它页面复用的插画组件和任务 API；保留对话内标题栏、输入区与独立滚动的消息区。
   执行过程沿用任务详情中的产物记录；未配置模型直接打开系统设置的 Agent 与模型分区。
   浏览器刷新后恢复上次打开的会话；针对已落库但仍在运行的轮次，短期轮询历史结果，不自动重发。
   Hermes 报告未完成或失败时写入网页对话失败状态；不要把模型响应体或调试数据当作回复落库。
4. Hermes 0.20.0 到上游稳定版 v0.23.4：先验证 provider、SQLite 会话续接、流回调、工具注册以及默认权限；不改已提交第三方目录。若需要改变第三方安装方式，版本、提交和依赖锁一起核验。
5. 逐阶段运行专项、构建和一致性检查。未发布时通过保留的基线分支回退；不覆盖用户目录。

## Hermes 升级关卡

2026-11-26 核对官方 GitHub 稳定版为 `v0.23.4`，提交 `8fc0374447313e276f6b9a2764bfc750190c966a`。隔离环境按上游锁安装成功；Xbot 联合解析失败：Python 3.14 下 Xbot 要求 `ruamel.yaml>=0.18.17`，上游固定 `0.18.16`；Anthropic 两边固定 `0.87.0` 与 `0.125.0`。现有 Docker 基础镜像仍为 Python 3.11，上游主要运行依赖的声明条件已变为 `>=3.14`。

新版保留三个流式/工具回调构造参数，但旧 `SessionDB.resolve_resume_session_id` 不再存在；`resolve_provider_client` 新增 `task` 与 `pool_choice`。新版还存在独立于 Xbot 当前 `model_tools.handle_function_call` 包装器的内联分发。上线前需覆盖 admin/member/guest 的允许与拒绝路径，验证 provider 与 SQLite 历史迁移，不可仅靠能回复文本判定升级成功。

建议先就受控依赖与 vendor 更新方式确认范围；用既有 `scripts/sync_hermes.py` 固定版本、提交和归档哈希，不手工维护第三方源码。先在临时数据库和独立镜像里跑通依赖解析、上下文续接、产物及权限回归，再以同样配置验真实模型。回滚需要同时保留旧镜像、配置和升级前的会话库备份；不得让旧版本打开可能已迁移的新数据库。本轮没有切换依赖、镜像或会话库。
